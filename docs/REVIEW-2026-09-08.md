## 1. The finding that matters: a boss that does nothing passes all four gates

`packages/harness/test/fixtures/jitter.js` is five lines. It never attacks, never approaches, never
uses a cooldown. It twitches 0.02 px left and right, forever.

```bash
pnpm harness packages/harness/test/fixtures/jitter.js --round 2 \
  --summary packages/harness/test/fixtures/summaries/camper-round1.json
```

```
✓ Gate 1 static 3ms
✓ Gate 2 fuzz 58ms
✓ Gate 3 balance 2295ms
  panel 0.44 (Camper 0.76, Kiter 0.00, Rusher 0.00, Dodger 1.00) · Mimic 1.00 · band 0.35-0.50 · idle run 0t/90
✓ Gate 4 perf 62ms
APPROVED — 4 gates passed
```

Against the four real replay summaries in `packages/harness/test/fixtures/summaries/`,
this boss is **APPROVED for `camper-round1` and `dodger-round1`** (Mimic 1.00 both) and
rejected only for `kiter` and `rusher`. Camper and dodger are the two passive styles — how
a first-time player at a demo booth actually plays. So the failure is not a rare corner: it
is the modal path for a nervous judge holding the mouse.

Note what the gate reports while approving it: `idle run 0t/90`, `p90 0%` — ACTIVE says the
boss is 100 % active — and `Mimic 1.00`, which the UI renders as the boss having adapted
*perfectly* to the player.

### Two compounding causes, and one correction

**Correction to an earlier draft of this section, which said the `0.02` was sneaking
under `STILL_EPSILON` (0.01 px).** It is not. `validateMove` normalizes `move` to a unit
vector — [validate.ts:163](../packages/contract/src/validate.ts#L163), "a strategy may
return any magnitude" — so the magnitude is discarded and the boss steps its full
2.6 px/tick. The strategy is genuinely moving at top speed and ACTIVE's per-tick clause is
working exactly as written. Raising the threshold to a fraction of boss speed was tried
and measured to change the idle run of *none* of the eleven shipped strategies, because
`move` is either full-speed or wall-clamped to nothing; it was reverted.

1. **Both of ACTIVE's clauses are about *stalling*, and this boss never stalls.**
   `maxIdleRun` and `idleFractionP90` measure consecutive and aggregate motionless ticks.
   An oscillating boss has zero of both — the best possible score — while standing on one
   tile. Nothing measured *where it got to*.
2. **`bossWon: state.outcome !== 'playerWon'`** — [runMatch.ts:77](../packages/harness/src/sim/runMatch.ts#L77).
   Timeout is a boss win. A boss that never attacks beats any bot that fails to kill it in
   60 s, so passivity is *rewarded* by the band. This is why Camper reads 0.76 and Dodger
   1.00 against a boss doing literally nothing.

And the signal that would have caught it existed: **`minTravelPx` was dead code**, written
at [simulate.ts:349](../packages/harness/src/sim/simulate.ts#L349) and read nowhere —
`grep -rn minTravelPx packages/harness/src` returned five writes and zero reads. Path
length is the wrong metric anyway (the jittering boss accumulates ~9 000 px of it inside a
5 px box), but the *intent* was right and never wired up.

### This answers question 4 directly

The ACTIVE gate is a patch, not a control. It closed the *instance* the playtest found
(`return {type:'idle'}`) and left the *class* open (a boss that is motionless in every sense
a player cares about). A deterministic control that can be satisfied by 0.02 px of jitter is
measuring the wrong thing, and it was added under playtest pressure rather than derived from
what "the boss is playing" means.

The deeper problem is cause 2, and it is a balance-design problem, not a gate problem:
`timeout = boss win` makes "do nothing" a viable strategy in the sim and a broken boss on
screen. The bots reward exactly the behaviour the game must never ship.

**Fix, ~2 hours, highest value in the repo:** add an ACTIVE clause on boss *displacement* (a
boss must range some floor of ground per match), and separately decide whether a timeout should
count as a boss win at all — a draw, or partial credit weighted by remaining boss HP, removes
the incentive rather than papering over it.

*Done, half of it.* ACTIVE now asserts `minSpanPx` ≥ the boss's own diameter (56 px); measured
headroom is 2.8× to the narrowest shipped strategy and 21× to the attack. The timeout rule was
left alone on purpose — see the status table at the top for why.

## 2. "Four deterministic gates" is true of one of them

The f67e448 fix injected `monotonicClock()` at exactly three call sites, all in the Gate 3
simulator: [runMatch.ts:158](../packages/harness/src/sim/runMatch.ts#L158),
[simulate.ts:202](../packages/harness/src/sim/simulate.ts#L202),
[worker.ts:52](../packages/harness/src/sim/worker.ts#L52).

Gate 2 loads with `opts.sandboxOptions ?? {}` — [gate2Fuzz.ts:267](../packages/harness/src/gates/gate2Fuzz.ts#L267).
Gate 4 does the same — [gate4Perf.ts:131](../packages/harness/src/gates/gate4Perf.ts#L131).
Both therefore fall through to the sandbox default `() => performance.now()`
(`loadStrategy.ts:108`), i.e. host wall clock. `grep -rn monotonicClock packages/agents/src/loop.ts
packages/harness/src/cli.ts` returns nothing — neither the CLI nor the autonomous loop
overrides it.

Measured consequence. A strategy doing N iterations of arithmetic per `decide`:

| N | Gate 2 |
|---|---|
| 20 000 | ✓ passes (334 ms) |
| 30 000 | ✓ passes, 5 consecutive runs |
| 40 000 | ✗ rejected — over budget on **4 of 560** states |
| 60 000 | ✗ rejected — 7 of 560 |

Gate 2 rejects on *any single* runner failure ([gate2Fuzz.ts:350](../packages/harness/src/gates/gate2Fuzz.ts#L350)).
A strategy in that band is approved or rejected by how loaded the machine is. That is also the
exact flake `packages/server/test/fallback.test.ts` already works around by capping its worker
count so it does not deschedule the harness suite — the workaround is in the repo, the cause
is not fixed.

Gate 3 itself is genuinely reproducible: three identical `pnpm harness` runs produced
byte-identical output (md5 match on the panel line). The fix is real; the umbrella claim is not.

**Fix: one argument each.** `sandbox.load(source, { now: monotonicClock(), ...opts.sandboxOptions })`
in gate2Fuzz.ts:267. Gate 4 is arguably meant to measure real time — if so, say so in SPEC and stop
calling it deterministic, and note that its p99 verdict is not portable across machines.

## 3. What holds up under attack — and this part is strong

Eight bypass attempts written and run against Gate 1 and the sandbox:

| Attempt | Result |
|---|---|
| `globalThis['Da'+'te']` | Gate 1: `forbidden identifier 'globalThis'` |
| `new Function('...')` | Gate 1: `forbidden identifier 'Function'` |
| indirect `eval` | Gate 1: `forbidden identifier 'eval'` |
| `import('node:fs')` | Gate 1: `dynamic import() is not allowed` |
| `(function(){}).constructor('return 7')()` | **passed Gate 1**, died in the sandbox: `'not a function'` |
| `{dx: 0/0, dy: 1/0}` | Gate 2: `move.dx must be a finite number, got NaN`, 560/560 |
| throwing getter on `.type` | Gate 2: `unknown action type: "dash"`, 280/560 |
| throws once at tick 300 | Gate 2 found it: `1/560 states (first at state 386: tick 300, …)` |

The prototype-chain attack is the interesting one: Gate 1 misses it, and it fails anyway
because `packages/sandbox/src/quickjs.ts:56-65` removes `Date`, `RegExp` and `Proxy` as
**intrinsics** (no prototype chain leads back) and `prelude.ts:214-220` strips `.constructor`
from all four function prototypes. There are no host bindings at all — `rand()` is pure JS
inside the VM. The defence-in-depth argument in `staticCheck.ts`'s header is not decoration;
it is load-bearing and it held.

Gate 1 does have a stated-completeness gap: `staticString()` resolves only literals,
templates and `+` concatenation, so `obj[String.fromCharCode(...)]` is invisible to it. Harmless
here for the reason above, but "AST analysis defeats obfuscation" is really "defeats literal
concatenation".

Also verified holding up:

- **`pnpm verify` green in 62 s**, and the test count is **990** (contract 206, agents 215, web 191,
  harness 118, sandbox 100, engine 91, server 69) — the handoff's number, not the README's.
- **`pnpm test:e2e` 18/18 passed** in 31 s, including `browser and Node agree on the replay hash`.
  AC3 is genuinely met.
- **AC1 met.** Fresh `git clone` → `pnpm install` → server boots with no key:
  `agents: FALLBACK-ONLY — REMATCH_PROVIDER=none — fallback-only by configuration (no model will be called)`.
  Honest log line, honest health payload (`hasApiKey: false`).
- **Fallback pool measured**: all 8 land in their round's band with ≥0.03 margin and `idle run ≤1t/90`
  (`pnpm --filter @rematch/server exec vitest run fallback`). This substantiates §3's balance claim —
  at 120 matches, not the 200 the handoff cites; 200 is checked by hand, per the test's own comment.
- **No path mislabels a fallback as approved.** `loop.ts:468-484` sets `approved:true` only after all
  four gates plus a successful `readMeta()`, and gives up rather than shipping a strategy whose meta
  the interlude cannot render. `handleRewrite.ts:284-291` attaches a fallback only when `!approved`.
- **Rejection feedback is genuinely structured**, not a nudge. Real output:
  `0.75 vs panel — too hard (band 0.35–0.50 for round 2; Camper 1.00, Kiter 0.88, Rusher 1.00,
  Dodger 0.12); boss motionless for 98 consecutive ticks (1.6 s) vs Dodger — never return idle as a
  resting state; patrol, reposition or feint instead (limit 90 ticks)`. That is a directive a model
  can act on.
- **Context isolation is structural.** The Coder path imports nothing from `@rematch/engine`; the
  Analyst path never touches `prevSource` or the contract doc. `contract` has zero deps by design, so
  a doc assembled from its README + `types.ts` cannot leak an internal even by accident. The denial
  tests read the engine's **actual barrel file at test time** and assert none of its exported names
  appear — that auto-updates when the engine grows, which is a better test than a hardcoded list.

## 4. Docs and artifacts do not match the code

This is the cheapest damage in the review to fix and the most expensive to be caught on.

1. **`README.md:8`: "897 tests + 14 e2e".** Measured: 990 and 18. Also at README:85 and README:156.
   A judge who runs `pnpm verify` sees the banner is wrong in the project's favour, which invites
   them to check everything else.
2. **`docs/SYSTEM.md:459-461`** describes the evidence file as "the complete event log of this **and
   the nine other runs** in the same eval". The file contains **one** run, and its own `note` field
   reads: *"Trimmed to the run quoted in docs/SYSTEM.md §6; full artifact had 10 runs (passRate 0.6)."*
   `README.md:140` repeats the claim ("all ten runs, every rejection, every generated `strategy.js`").
   The other nine runs and their generated files are not in the repo.
3. **`docs/SYSTEM.md:782` contradicts `docs/SYSTEM.md:457`** in the same file: *"No real API run has
   been recorded (AC 6)… has never been run against a live key"* against §6's *"A real run. OpenAI
   `gpt-5.4-mini`… 7 model calls… No human message anywhere."* The `Honest list, at 069be8d` marker
   does not rescue this — item 10 in the same list carries a "FIXED 2026-09-04" strikethrough dated
   after that commit, so the list has been edited since and this item was missed.
4. **Nothing was ever pushed.** `git rev-parse origin/main` = `4398e6e` — the spec template. All
   thirteen implementation commits, every doc, and the evidence file exist only in local history.
   CI has never run, of any kind, against this code. That costs more than AC9: `.githooks/pre-commit`
   argues its own `--no-verify` hatch is acceptable *because* "CI re-runs the same script on every push
   and PR, so a `--no-verify` commit buys minutes, never a merge." That sentence is currently false, so
   the one deterministic control over `main` is a bypassable local convention with no backstop.
5. **The 90 s deadline the handoff credits for the live results is unreachable through the UI.** The
   client aborts at `INTERLUDE_DEADLINE_MS = 45_000`
   ([interlude/index.ts:79](../packages/web/src/interlude/index.ts#L79)) while `.env` sets
   `REMATCH_DEADLINE_MS=90000`. So the two live successes at 38.7 s and 42.2 s were 45 s-compliant with
   ~3 s of margin, and any attempt between 45 s and 90 s shows the player a fallback while the server
   keeps working. The extra 45 s buys nothing the UI will accept.
6. **Heat map**: SPEC:116 and SYSTEM:137 both say "rolling"; `step.ts:166` says
   `// Position heat: accumulated counts` and never decays. Flagged as a delta in the handoff — but
   SPEC §13's 17 deltas do **not** actually contain this one; only the sum-to-1 normalization is listed.

## 5. Answers to the seven questions

**1. Where does it over-claim?** Three places, in order: "four deterministic gates" (one is),
"the complete event log of all ten runs" (one run), and "897 tests" (990). The ACTIVE gate is
over-claimed by implication rather than by sentence — nothing says it catches a frozen boss, but
its entire existence in the narrative is that it does.

**2. Demonstrated or asserted?** Half-demonstrated, and the demonstration is real: 990 tests, an
AST checker plus an intrinsic-stripped VM that survived eight attacks, a byte-reproducible Gate 3, and
an autonomous loop with structured feedback and no human path. What is asserted rather than
demonstrated is the *sufficiency* claim — that passing the gates means the output is safe to ship.
`jitter.js` is a five-line counterexample: it passes every gate, satisfies ADAPTED at 1.00 against
two of four real player replays, and is a boss no player would accept.

**What a skeptical judge pokes at first:** not the code. `git log origin/main` — one commit, a spec
template. Then `pnpm verify` versus the README banner. The technical holes above take an hour to find;
those two take ninety seconds and set the tone for everything after.

**3. Is 0.6 disqualifying?** No, and the fallback genuinely covers it — the UI never pretends the model
worked, and the copy is specific (`"Using a pre-approved strategy — the coder timed out."`). But the
number the design should be judged on is not 0.6, it is the *reason*: three of four failures ended on
`deadline`, not `max-attempts`. So the bands are not too narrow and the bots are not the binding
constraint — Coder latency against the clock is (p50 7.7 s, p90 12.3 s, up to 4 attempts × K=3). The
design is not wrong; the latency budget is. Two cheap levers: start the Analyst while the round-won
screen is still on screen, and let the interlude's beats stretch honestly rather than hard-aborting at
45 s. Neither needs a model change.

**4. Is ACTIVE legitimate?** No — see §1. It is a patch, and the thing it patches over is
`timeout = boss win`.

**5. Would a mixed jury follow the interlude in 90 s?** The shape, yes: four labelled beats, a diff of
real JS, per-gate rows, a big ✓/✗ stamp, and a plain-English rejection sentence. A non-technical viewer
will come away with "the AI rewrote the boss and something rejected a draft," which is the point.
The numbers will not land — `panel 45% · mimic 75%`, `band 0.35–0.50`, `candidate 2 of 3`, token counts
— and nothing on the interlude screen explains them; the only gloss is the start screen's four-step
primer, shown once, before Round 1. Two half-hour fixes: put a one-line "what this means" under the
gate meter, and put the always-on debug HUD footer (tick counts, seeds, `d 0.03/0.11ms`, idle %,
violation counts, visible during every normal fight) behind `?debug=1`. Its comment says the choice is
deliberate — *"the judges asked for determinism, so show it"* (`hud.ts:151`) — and that reasoning is
sound for the technical half of the jury and wrong for the other half, who read it as an unfinished
screen. A flag gets both: default clean, `?debug=1` in the technical walkthrough.

**6. Six days — cut and fix.**

*Fix, in this order:*
1. Wire `minTravelPx` into ACTIVE, and reconsider `timeout = boss win`. (~2 h) — §1.
2. `monotonicClock()` into Gate 2, and either fix or re-describe Gate 4. (~1 h) — §2.
3. `git push`. Let CI run once. (~30 min, and it repairs the pre-commit hook's own argument.)
4. README 897→990; reconcile SYSTEM §6 with §9 item 1; either commit the full ten runs or describe
   the file as the excerpt it says it is. (~1 h)
5. Re-record the demo runs after fix 1. The current recordings show frozen bosses, disclosed in
   9 px fine print in the busiest corner of the screen — on a projector that reads as the bug, not
   as the disclosure. (~2 h)
6. Debug HUD behind a flag; one line of "what this means" under the gate meter. (~1 h)
7. Any audio at all — a hit, a telegraph, an approval stamp. Three sounds. Currently `grep -riE
   "audio|\.mp3|\.wav"` over `packages/web/src` returns nothing. Cheapest Product Quality points
   available. (~2 h)

*Cut:* the K=3-as-parallel-workstreams framing (see 7 — present it as what the code says it is);
rounds 3–5 loop ambitions (bands and fallbacks are enough, and SYSTEM §9 item 4 already says so
honestly); Round 1 rebalancing (it is a tutorial and that is defensible — say so out loud instead of
apologising for it).

*On AC9:* deploying the server means shipping `/api/rewrite` with no auth, a rate limit that trusts
the first `x-forwarded-for` entry, and an in-memory daily cap that resets on restart — with player-controlled
`prevSource` (64 kB) going verbatim into the Coder prompt inside a `js` fence. For 5 rubric points that
is a bad trade. Deploy the **static web build only**, defaulting to `?agent=recorded`: you get a real
URL, real recorded runs, and zero spend exposure. Thirty minutes, after fix 5.

**7. Unnecessary complexity.** Two things, both honest in the code and oversold in the framing:

- **K=3 "parallel candidates" is best-of-N sampling.** All three calls get the byte-identical system
  prompt and a near-identical message differing by one instruction line; the gates then run
  *sequentially* by explicit design (`loop.ts:355-361`). The code comment gives the real motivation —
  variance reduction inside a narrow band — and that is a good reason. Calling it a parallel workstream
  for the Agentic axis invites a judge to look, and what they find is one agent sampled three times.
  Worse, K degrades toward 1 exactly under deadline pressure (`CANDIDATE_GATE_RESERVE_MS`,
  `loop.ts:118`), so the mechanism weakens precisely when the loop is closest to failing.
- **The Mimic proves less than it appears to.** It is a hand-authored bot driven by three summary
  statistics with fixed constants (`RESAMPLE_TICKS=70`, formulaic hold/dash rates). ADAPTED ≥0.70 says
  "beats a formulaic reconstruction of last round," not "generalises to this player." `jitter.js`
  scoring 1.00 against two of four real summaries is the proof: the metric is satisfiable without
  adapting to anything.

Everything else earns its place. The seven packages are not padding — `sandbox` as its own package is
what makes the security boundary auditable, `contract` having zero dependencies is what makes the
Coder's context provably clean, and the 36 700 lines are unusually well-commented for hackathon code.
The comment density is doing real work: several of the findings above came from a doc comment that
honestly described a limitation the surrounding docs then over-claimed past.
